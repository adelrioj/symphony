The tracker is the scheduler:
Symphony against Orca and Grok Bot

Three products described as "agents that work while you're away." They sit at three different layers, and only one of them derives what should run from the state of your issue tracker.

Verdict. These are not competitors. Symphony is a headless delivery daemon bound to a board. Orca is an agent IDE whose automations are cron over git worktrees. Grok Bot is a hosted general-purpose agent with OAuth plugins and a cloud browser. Symphony and Orca compose; Grok Bot solves a different problem.

Control flow

Who decides that work starts

Symphony

The differentiator is a specified control loop, not a coding agent

Symphony ships no model and no editor. What it ships is SPEC.md — 2,414 lines of RFC 2119 normative text — plus an Elixir/OTP reference implementation that may be a superset of the spec but must never conflict with it. The spec pins the tracker and agent boundaries as adapter contracts, so "which board" and "which coding agent" are both configuration. The mechanics other tools leave implicit are pinned:

Claim state machine (§7.1)

Unclaimed → Claimed → {Running, RetryQueued} → Released, mutated by a single authority — one stateful Orchestrator GenServer. Duplicate dispatch is impossible by construction, not by convention.

Concurrency (§8.3)

available_slots = max(max_concurrent_agents - running_count, 0)
# per-state override, else fall back to the global limit
max_concurrent_agents_by_state[state]

# candidate ordering
priority asc (null last) → … → identifier lexicographic

Retry and backoff (§8.4)

# clean worker exit — re-check whether the issue is still active
delay = 1000 ms

# failure-driven
delay = min(10000 * 2^(attempt - 1), agent.max_retry_backoff_ms)
#                                    default 300000 (5 min)

Reconciliation, every tick (§8.5)

Stall detection against codex.stall_timeout_ms (measured from the last agent event, else started_at); then a tracker state refresh — terminal state kills the worker and cleans the workspace; a state that is neither active nor terminal kills the worker without cleanup. If the refresh call fails, workers keep running and it retries next tick.

Policy lives in the repo

WORKFLOW.md is YAML front matter plus a Liquid-templated prompt body. Invalid config at boot halts the process; an invalid file on hot reload is ignored and the last-known-good config is kept, so the BEAM reloads without stopping active agents. Config is reached only through SymphonyElixir.Config — never ad-hoc env reads.

Safety is normative

Workspaces must stay under the configured root and a turn's cwd must never be the source repo; the checks live in path_safety.ex. Recovery after restart is tracker-driven and filesystem-driven — there is deliberately no orchestrator database.

What it costs

One instance drives one project (a single tracker.project_slug and one repo); scale-out is one Docker container per WORKFLOW.md. Blocked entries live in memory and are cleared on restart. There is no inter-agent messaging and no human decision gate. The README labels it a low-key engineering preview for trusted environments, and it assumes a repo that already practices harness engineering.

Orca

Automations are the thin part; orchestration is the real overlap

The scheduling surface is exactly that — a scheduler. It is well-shaped: create disabled, tune, then enable.

orca automations create \
  --name "Weekday triage" \
  --trigger weekdays --time 09:00 \
  --prompt "Triage new issues and summarize blockers" \
  --provider codex --repo my-repo \
  --precheck "gh pr list --json number -q .[0].number" \
  --disabled --json

Plus --timezone, --workspace targeting instead of --repo, --missed-run-grace-minutes, --reuse-session versus --fresh-session, run history via automations runs, and a manual Rerun. A non-zero --precheck exit records a skipped run — the closest thing to a conditional trigger, and it is a shell probe you write yourself.

The layer that actually overlaps Symphony is orca orchestration: a durable Run namespace with a coordinator inbox, Tasks (pending/ready/dispatched/completed/failed/blocked) with dependencies, Dispatches that hold lifecycle authority, typed messages, and decision gates.

Orca has, Symphony doesn't

  • Inter-agent messaging and group addresses (@all, @idle, @codex)
  • Blocking ask with enumerated options, and coordinator-owned gates that block a task until resolved
  • Task DAGs with explicit dependencies
  • Federated workers placed on remote SSH hosts
  • A first-class human review surface — diff viewer, attribution, commit/push

Symphony has, Orca doesn't

  • An external source of truth: the board decides what exists and when it ends
  • Specified backoff, stall detection, and per-tick reconciliation
  • Restart recovery without a database, derived from tracker + filesystem
  • A portable spec you can reimplement in any language
  • Headless operation — nothing to keep open

Recovery in Orca is "open the run and click Rerun." That is a reasonable product decision for a tool with a human at the keyboard; it is not a contract you can operate unattended against.

Grok Bot

Adjacent, not comparable

Persistent named agents, OAuth plugins (Gmail, Notion, Slack — scoped to the signing-in account and gate-able by a Cursor team admin), a cloud computer where the agent drives a browser you personally logged into, and a secrets store so credentials never land in chat.

There is no worktree, no git model, no diff review, and no published retry semantics — the routines help page returns 404; routines exist only as prose on the getting-started page. It is a general knowledge-work agent that happens to be able to code, not a system for landing pull requests unattended.

The single axis where it meets Symphony is the promise that work continues while you are away. Symphony's version of that promise is bounded, auditable, versioned in the repository, and terminated by tracker state. Grok Bot's version is a conversation you come back to.

Choosing

Pick by who owns the queue

  1. Board-driven, unattended, auditable delivery → Symphony. The only one where "what should run" is derived from tracker state rather than a clock or a human, and the only one shipping a portable spec so the behavior survives a rewrite in your language.
  2. You intend to watch and review → Orca. Automations are a thinner scheduler, but the orchestration primitives — DAGs, gates, blocking ask, federated SSH workers — are richer than Symphony's flat dispatch loop, and the review surface is real.
  3. Non-repo knowledge work with SaaS side effects → Grok Bot. Not a candidate for load-bearing code delivery.

They compose — with one hard constraint

Symphony has no inter-agent messaging and no human decision gate: an issue either progresses or lands in blocked_state. Orca has no tracker-state control loop. Running Symphony as the ingest and scheduling authority while using Orca-style worktrees for human review is coherent.

What is not coherent: pointing an orca automations cron and a Symphony poller at the same board. You get two claim authorities with no shared lock, and Symphony's duplicate-dispatch guarantee — which holds only because one GenServer serializes every state mutation — evaporates.
